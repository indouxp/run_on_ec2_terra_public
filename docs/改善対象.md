## 対応方針の詳細

### 複数 AZ（A-1）の位置づけ

本システムの EC2 は **13分程度だけ稼働して自己削除する使い捨てインスタンス**であり、常時稼働する「守るべきサービス」が存在しません。
そのため「可用性のための複数 AZ 冗長化」は意味が薄いと判断しました。

| 観点 | 実態 |
|------|------|
| EC2 | 使い捨て。AZ 障害が起きてもジョブが落ちるだけで、入力は S3 に残るため再実行で復旧 |
| S3 / Lambda | 元々リージョンサービスで AZ 跨ぎ冗長化済み。単一 AZ なのは EC2 とサブネットのみ |
| 実行頻度 / SLA | 月8回・SLA なし。可用性投資は回収できません |

ただし `c6i.4xlarge` のような大きめのインスタンスは、特定 AZ で **InsufficientInstanceCapacity（容量不足で起動失敗）** が稀に起きます。
複数サブネットを用意して「AZ-a が不可なら AZ-c で起動」とすれば**起動成功率**を上げられます。
→ これは**可用性ではなく「起動の保険」**であり、A-4（複数ジョブ同時処理）で複数インスタンスを立てる際に効いてきます。
**したがって A-1 は A-4 に従属する項目とし、単独では導入しません。**

### 「並列化」の2軸 — A-5（高速化）と A-4（同時処理）は別物

「並列化」と一口に言っても、解く問題が異なる2つの軸があります。混同しないように区別します。

| 軸 | 解く問題 | 手段 | インフラ変更 | 位置づけ |
|----|----------|------|:------------:|----------|
| **A-5** | 1ジョブを**速く**（コアを使い切る並列） | `run.sh` のチューニング | 不要 | 次期機能ではない。いつでも可能な最適化 |
| **A-4** | **同時に複数ジョブ**を捌く（並行） | 複数インスタンス | 必要 | 今後の拡張候補。要否未確定 |

**重要な前提：**
- 拡張として検討する「並列実行」は、**A-4（複数ジョブの同時処理）** を指します。現状の Lambda が「同名タグのインスタンスが起動中ならブロック」して**意図的に1ジョブずつ直列化**しているのを緩める話です。
- 一方 **A-5 は「次期機能」ですらありません**。c6i.4xlarge は最初から16コアあり、それを `run.sh` で使い切るのは単なる最適化で、いつでもできます。

### A-5（1ジョブの高速化）

c6i.4xlarge は16 vCPU です。`run.sh` 内で `pigz -p` / `ffmpeg -threads` / `xargs -P` 等を使えば、**追加インフラなしで並列化**できます。
**月8回・1ジョブずつの運用なら、A-5 だけで完結し A-4 は不要、という結論が最も自然です。** まずここを確認します。

### A-4（複数ジョブの同時処理）

> **要否は必要になった時点で判断します（現時点で未確定／実施しない見込み）。**
> 同時アップロードが実際に発生する需要が出たときのみ検討します。

実施する場合の方式は以下のとおり整理済みです。

| 方式 | 中身 | 複雑性 | 採否 |
|------|------|:------:|:----:|
| B. ジョブ単位で複数インスタンス | `.conf` 1つ → インスタンス1台。複数ジョブを同時処理 | 中 | ⭕ 実施するならこれ |
| C. 1ジョブを複数台に分割 | 入力分割 → 複数台 → 結果マージ | 高 | ❌ 採用しません |

**方式 C を採用しない理由：**
1ジョブを複数 VM に分割すると、入力分割・結果マージに加えて
**「片方が失敗したらもう片方が肩代わりする」フェイルオーバー機構**が必須になります。
MapReduce を自前実装するに等しく、得られる効果に対して機構が重すぎます。

**方式 B を採る場合の要点：**
現状の「同一 `ec2_instance_name_tag` の起動チェック」を**タグごと**に緩めるだけです。
各ジョブは独立した処理単位のため、**分割・マージ・フェイルオーバーは不要**です。1台落ちても**そのジョブだけ再実行**すれば済みます。
各インスタンスが独立しているため、起動時に AZ を選び容量不足なら別 AZ で再試行する（A-1）だけでよく、**共有状態が無いのでフェイルオーバー機構が要りません**。これが複数 AZ が意味を持つ唯一の現実的な形です。
