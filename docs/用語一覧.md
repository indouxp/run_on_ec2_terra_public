## Terraform 関連

| 用語 | 説明 |
|:-----|:-----|
| HCL | HashiCorp Configuration Language。Terraform の設定記述言語。`.tf` ファイルで使います。JSON に似るが別物（`=` 代入・カンマ不要・コメント可）。代替として JSON 形式（`.tf.json`）もある |
| ルートモジュール（root module） | `terraform` を実行するカレントディレクトリ単位の構成。本プロジェクトでは `infra/`・`infra/bootstrap/`・`infra/backend/` の3つが別々のルートモジュール（state も init も別。infra は S3、bootstrap / backend はローカル state） |
| プロバイダ（provider） | AWS 等の API を操作するプラグイン。`terraform init` でダウンロードされ、`apply`/`plan` 時に API を直接呼びます。AWS CLI は経由しません |
| `terraform init` | プロバイダ取得・バックエンド初期化・lock ファイル生成を行います。ディレクトリ（ルートモジュール）ごとに必要。冪等 |
| `terraform fmt` | `.tf` ファイルを標準スタイル（インデント・引数の縦揃え等）に自動整形するコマンド。コードの内容や意味は変えず、体裁だけを揃えます。`-check` を付けると整形せず「整形が必要か」だけを終了コードで返します（CI 向け）。`-recursive` でサブディレクトリも対象。AWS 認証情報・`init` 不要。本プロジェクトでは各リソース追加後に実行し差分をゼロに保つ |
| `terraform validate` | 設定（`.tf`）の**構文**と**内部整合性**（存在しない属性・型不一致・未定義変数・参照先リソースの有無など）を静的に検証するコマンド。`init` 済みが前提（プロバイダのスキーマを使うため）だが**AWS へは接続せず認証情報も不要**、実リソースの状態や名前重複・権限までは見ません（それは `plan`/`apply` の役割）。`fmt` が体裁、`validate` が正しさ、と役割が分かれる |
| `terraform plan` | 適用前に変更内容（add/change/destroy）を表示します。読み取り専用で AWS を変更しません |
| `terraform apply` | 実際に AWS リソースを作成・変更・削除します |
| state（`terraform.tfstate`） | Terraform が管理するリソースの現状記録。実リソースと設定の対応を保持し、差分管理の基準になります。機微情報を含むため Git 管理外。`infra/` の state は S3（`ts-030-bkt-tfstate` の `infra/terraform.tfstate`）、bootstrap / backend はローカル。詳細は [Terraform_stateの仕組み](Terraform_stateの仕組み.md) |
| `import` ブロック | 既存の実リソースを state に取り込む宣言（Terraform 1.5+）。`to`（リソースアドレス）と `id`（実リソースの ID）を書き、`plan` で取り込み結果を確認してから `apply` します。state 消失時の復旧に使用（BUG-003） |
| リモートバックエンド | state を S3 等の共有ストレージに置く設定（`backend` ブロック）。端末故障による消失を防ぎ、ロックで同時実行も防ぎます。本プロジェクトは `infra/` の state を S3（`ts-030-bkt-tfstate`）に置きます。backend ブロックでは変数を使えないため値を直書きします |
| `use_lockfile` | S3 バックエンドのロック方式（Terraform 1.10+）。実行中に `<key>.tflock` オブジェクトを作成して排他し、終了時に削除します。従来の DynamoDB テーブルが不要 |
| `terraform init -migrate-state` | backend 設定の変更時に、既存の state を新しい backend へコピーするオプション。`-force-copy` で確認プロンプトを省略できます |
| `prevent_destroy` | `lifecycle` ブロックの設定。そのリソースを破棄する plan をエラーにして、Terraform からの誤削除を防ぎます。state 用バケットに使用 |
| `force_destroy` | `aws_s3_bucket` の引数。destroy 時にバケット内のオブジェクトを全削除してからバケットを消します。本プロジェクトは CloudTrail ログ用バケットのみ `true`（監査ログも消えます）。実行主体に `s3:DeleteObject`／`s3:DeleteObjectVersion` が必要（BUG-004） |
| `default_tags` | provider に指定すると、そのプロバイダで作る全リソースに共通タグを自動付与します。本プロジェクトでは `Project=ts-030` を一括付与 |
| `assume_role`（provider） | provider が起動時に別の IAM ロールを引き受けて実行する設定。本プロジェクトでは infra 実行ユーザー `ts-030-usr-build` から `ts-030-role-build` を引き受ける |
| data source | 既存リソースや情報を参照するための読み取り専用ブロック。例：`data "aws_caller_identity"` でアカウント ID を取得 |
| `hashicorp/http` プロバイダ | HashiCorp 公式の Terraform プロバイダの1つ（名前は `http`）。`data "http"` データソースを提供し、Terraform 実行時に任意の URL へ HTTP リクエストを送りレスポンス本文を取得できます。`aws` プロバイダとは別物なので `required_providers` への追加と `terraform init` が必要 |
| `data "http"` | `hashicorp/http` が提供するデータソース。指定 URL へ HTTP GET し `response_body` に本文を格納します。本プロジェクトでは SG の SSH 許可元に使う実行元グローバル IP の取得に利用（`https://checkip.amazonaws.com`） |
| `jsonencode()` | HCL のオブジェクトを JSON 文字列に変換する関数。IAM ポリシー定義で使用 |
| ブートストラップ | 「自分が AssumeRole するロールを自分で作れない」循環を解くため、ロール作成だけを先に行う初期構築。`infra/bootstrap/` が該当 |

## AWS ネットワーク関連

| 用語 | 説明 |
|:-----|:-----|
| VPC | 仮想プライベートネットワーク。本プロジェクトは `ts-030-vpc-010`（CIDR `10.0.0.0/16`、DNS hostnames/support 有効） |
| サブネット | VPC 内のネットワーク区画。`ts-030-subnet-010`（CIDR `10.0.1.0/24`）。単一 AZ 構成 |
| IGW（インターネットゲートウェイ） | VPC をインターネットに接続するゲートウェイ。`ts-030-igw-010`。VPC にアタッチして使う |
| ルートテーブル | サブネットの通信経路を定義する表。`ts-030-rtt-010` に `0.0.0.0/0 → IGW` を設定。VPC のメイン RT は編集せず、専用 RT を新規作成してサブネットに明示的に関連付けます（経路を Terraform の管理下に置くため） |
| CIDR | IP アドレス範囲の表記法（例：`10.0.0.0/16`） |
| AZ（アベイラビリティゾーン） | リージョン内の独立した物理拠点。本プロジェクトは `ap-northeast-1a` の単一 AZ。複数 AZ は改善対象 A-1 として A-4 従属で検討 |
| セキュリティグループ（SG） | リソース（EC2 等）単位の仮想ファイアウォール。許可ルールのみを列挙し、明示されない通信は拒否する（ステートフル：戻り通信は自動許可）。本プロジェクトは `ts-030-sg-010`。インバウンドは SSH(22) を実行元グローバル IP のみ許可、アウトバウンドは全許可 |
| インバウンド / アウトバウンド | インバウンド＝リソースへ入ってくる通信、アウトバウンド＝リソースから出ていく通信。SG では別々にルールを定義します。本プロジェクトは SSH の受信のみ絞り、送信（S3/SNS 等への外向き）は全許可 |
| 実行元グローバル IP | `terraform apply` を実行するマシンがインターネットから見えるときのグローバル IP アドレス。`data "http"` が `https://checkip.amazonaws.com` へアクセスし取得します。これを `/32` にして SG の SSH 許可元に設定します。AWS 側ではなく手元マシンから取得される点に注意 |

## AWS S3・Lambda 関連

| 用語 | 説明 |
|:-----|:-----|
| S3 バケット（in / out） | オブジェクトストレージの入れ物。データ用は入力 `ts-030-bkt-in`・出力 `ts-030-bkt-out` の2つ（ほかに CloudTrail ログ用 `ts-030-bkt-cloudtrail-logs`、state 用 `ts-030-bkt-tfstate`）。バケット名は**グローバル一意**。`for_each` で共通設定をまとめて生成 |
| バケットポリシー | バケットに付けるリソースベースのアクセス制御。本プロジェクトでは **Deny フェンス**として使う（承認 principal 以外の data 操作を拒否）。許可(grant)は各ロールの IAM インライン、境界(fence)はバケットポリシー、という役割分担で多層防御にします。詳細: [ユーザーとロール一覧](ユーザーとロール一覧.md) |
| Deny フェンス（多層防御） | 本プロジェクトの S3 アクセス設計。バケットポリシーに `Effect:"Deny"` ＋ `Principal:"*"` ＋ `Condition StringNotLike aws:PrincipalArn [承認ARN群]` を置き、承認外の data 操作を拒否します。Deny 対象は data 操作のみ（管理系は除外）で `ts-030-role-build` はロックアウトされません。Allow のみのポリシーは「承認外を拒否」できず防御にならない（同一アカウントは OR 評価）ため Deny を使う |
| `aws:PrincipalArn` | ポリシー条件で使えるグローバル条件キー。リクエスト元プリンシパルの ARN に解決されます。assumed-role でも**ロール ARN**（セッション ARN ではない）に解決されるため、`StringNotLike` での principal 限定に確実で、`NotPrincipal`+`Deny` の取りこぼしを避けられます |
| パブリックアクセスブロック（PAB） | バケットの公開を防ぐ4つのスイッチ（`BlockPublicAcls`/`IgnorePublicAcls`/`BlockPublicPolicy`/`RestrictPublicBuckets`）。本プロジェクトは全て有効 |
| SSE-S3（AES256） | S3 が管理する鍵でのサーバサイド暗号化。KMS ではない既定の暗号化。`BucketKeyEnabled` で暗号化コストを削減。本プロジェクトの既定 |
| BucketOwnerEnforced（所有者制御） | ACL を無効化し、オブジェクト所有権をバケット所有者に強制する設定。ACL ではなくポリシーでアクセス制御する現行のベストプラクティス |
| ライフサイクル | オブジェクトを一定期間後に自動削除/移行するルール。本プロジェクトは Expiration のみ（Transition なし）で全体を `s3_expire_days`(既定30)日で削除。in/out 両方に適用 |
| S3 イベント通知（トリガー） | バケットのイベント（本プロジェクトは `s3:ObjectCreated:*`）を通知先へ送る仕組み。in バケットに `.conf` が置かれると Lambda を起動します。`aws_s3_bucket_notification` で定義 |
| Lambda リソースベースポリシー（`aws_lambda_permission`） | 「誰がこの関数を呼べるか」を関数側で定義する許可。S3 から起動するには principal `s3.amazonaws.com`・source_arn=バケット の許可が必須。Lambda ロール（実行時の権限）とは別物 |
| Lambda 実行ロール | Lambda が実行中に使う IAM ロール（`ts-030-role-lambda-010`）。in の .conf 読取・EC2 起動・PassRole・SNS/SES、起動待ちタイムアウト時の EC2 削除（`autogen-by` タグ付きのみ）の権限を持ちます。呼び出し許可（上の permission）とは役割が異なります |
| `archive_file` | `hashicorp/archive` プロバイダのデータソース。ディレクトリを zip 化して Lambda デプロイパッケージを作ります。`source_code_hash` に `output_base64sha256` を使うとソース変更時のみ再デプロイされます |
| `InstanceInitiatedShutdownBehavior` | EC2 が**自分自身の OS 側シャットダウン**（`shutdown -h now` 等）を行ったときの挙動を指定する起動パラメータ。`stop`（既定）＝停止して残る／`terminate`＝削除されます。本プロジェクトは起動 Lambda(`lmd-010`) の `run_instances` で `terminate` を指定し、ジョブ完了後の `shutdown -h now` でインスタンスを自己削除させる（EventBridge+終了 Lambda を不要化。詳細: [終了処理の簡素化.md](終了処理の簡素化.md)）。コンソール等からの API 停止には影響しません |

## AWS IAM・セキュリティ関連

| 用語 | 説明 |
|:-----|:-----|
| IAM ロール | AWS リソース／ユーザーが一時的に引き受ける権限のセット。`ts-030-role-build`（構築用）など |
| Trust Policy（信頼ポリシー） | そのロールを「誰が AssumeRole できるか」を定義するポリシー。`ts-030-role-build` はアカウントルートを信頼 |
| Permission Policy | そのロールが「何をできるか」（許可アクション・対象リソース）を定義するポリシー |
| AssumeRole | あるプリンシパルが別の IAM ロールの権限を**期間限定で借りて**、その間だけその権限で動く仕組み（`sts:AssumeRole`）。成立には「利用者のIDポリシー」と「ロールの Trust Policy」の**両方**が必要。借りた権限は一時キー（期限つき）。図入りの詳しい解説は [AssumeRoleまとめ](AssumeRoleまとめ.md) |
| インラインポリシー | ロールに直接埋め込むポリシー（独立した管理ポリシーではない）。`ts-030-role-build-policy` |
| Instance Profile | IAM ロールを EC2 にアタッチするための入れ物。EC2 は IAM ロールを直接持てず、Instance Profile 経由で関連付けます。本プロジェクトは `aws_iam_instance_profile.ec2`（名前はロールと同名 `ts-030-role-ec2-010`）。Lambda が同名で引いて EC2 起動時に付与します |
| マネージドポリシー / インラインポリシー | マネージド＝独立した再利用可能なポリシー（AWS 管理 or 顧客管理）。インライン＝ロールに直接埋め込む専用ポリシー。本プロジェクトは AWS 管理（`AWSLambdaBasicExecutionRole` / `CloudWatchAgentServerPolicy`）を `attachment` で付与し、固有権限は `aws_iam_role_policy`（インライン）で定義 |
| `iam:PassRole` | あるサービス（Lambda 等）が別のロール（EC2 ロール）をリソースに「渡す」権限。Lambda が EC2 起動時に `ts-030-role-ec2-010` を渡すために必要。渡せるロールを ARN で限定するのが最小権限の要点 |
| 最小権限の原則 | 必要な権限だけを与える設計原則。構築ロールは作成系が中心で ARN 事前特定が難しいため、本プロジェクトでは「6サービス限定 + 原則 `Resource:*`」とし、Administrator より絞る方針（state バケットと `ts-030-*` のオブジェクト削除は Resource を限定） |
| 明示的 Deny の優先 | IAM の評価では、どこかに `Deny` があれば `Allow` より優先されます。構築ロールは `s3:DeleteObjectVersion` を `Resource:*` で許可しつつ、state バケットだけ `Deny` して旧世代を消させない |
| `aws:SecureTransport` | リクエストが TLS（HTTPS）経由かを表す条件キー。state バケットのポリシーで `false`（非 TLS）のアクセスを全面拒否しています |
| バージョニング / `noncurrent_version_expiration` | S3 でオブジェクトの旧世代を残す機能と、旧世代だけを N 日後に削除するライフサイクル設定。state バケットで旧世代を保持し 90 日で削除 |
| Permission Boundary | IAM ロール／ユーザーが持てる権限の上限を定める仕組み。最小権限の厳密化手段（WBS 2.4 で検討） |
| Resource Groups Tagging API | タグ横断でリソースを検索する API（`aws resourcegroupstaggingapi get-resources`）。リージョン単位のため IAM 等グローバルサービスは対象外 |

## AWS 監視・証跡関連（WBS 2.8）

| 用語 | 説明 |
|:-----|:-----|
| CloudWatch Logs ロググループ | ログを束ねる論理コンテナ（`aws_cloudwatch_log_group`）。本プロジェクトは lambda/ec2/system の3種（`ts-030-log-lambda-010` 等）を作成し、保持期間は30日。KMS 暗号化は行わない（改善 S-1 を「不要」と判断）。実際に書き込まれているのは `ts-030-log-ec2-010` のみ（改善対象 B-6） |
| 保持期間（retention_in_days） | ロググループ内のログイベントを保持する日数。経過後は自動削除。本プロジェクトは全ロググループ30日 |
| メトリクスフィルタ | ログ内の特定パターン（本プロジェクトは `"ERROR"`）を検出して CloudWatch メトリクスに計上する仕組み（`aws_cloudwatch_log_metric_filter`）。名前空間 `ts-030/Lambda` 等・メトリクス `ts-030-lambda-errors` 等に `metricValue=1` で加算。**アラームは作成しない**（設計上の決定） |
| CloudTrail 証跡（Trail） | AWS API 呼び出しを記録・S3 に配信する監査ログ機構（`aws_cloudtrail`）。本プロジェクトは `ts-030-trail-010`。マルチリージョン＋グローバルサービスイベント有効。ログファイル検証・KMS は無し（SSE-S3） |
| 管理イベント / データイベント | 管理イベント＝リソースの構成変更等の操作。データイベント＝オブジェクトレベルの操作（本プロジェクトは全 S3 バケットの `AWS::S3::Object`）。`event_selector` で `read_write_type=All`・`include_management_events=true` を指定 |
| CloudTrail ログ用バケット | 証跡の配信先 S3 バケット（`ts-030-bkt-cloudtrail-logs`）。in/out と同様に PAB／SSE-S3／BucketOwnerEnforced を施し、`cloudtrail.amazonaws.com` に `GetBucketAcl`/`PutObject` を許可するバケットポリシーを付与。混同代理防止のため `aws:SourceArn`（当該トレイル）で限定。`force_destroy = true` のため terraform destroy で監査ログも削除されます |
| SNS 直接 publish（電話番号） | SNS トピックを経由せず `PhoneNumber` を指定して SMS を直接送る方式。本プロジェクトの SMS 通知はこの方式のため、SNS トピックは作成しません。IAM 上は特定トピックに絞れないため Lambda ロールの `sns:Publish` は `Resource="*"` とします |

## プロジェクト固有

| 用語 | 説明 |
|:-----|:-----|
| プレフィックス | リソース名の先頭に付ける識別子。本プロジェクトは `ts-030-` |
| Project タグ | 全リソースに付与する識別タグ。本プロジェクトは `Project=ts-030`。Terraform 管理外の Lambda 起動 EC2/EBS にも `lambda_function.py` が `Project=<prj_prefix>` を付与 |
| `autogen-by` タグ | Lambda が起動した EC2/EBS に付ける自動生成の目印。値は `<prj_prefix>-system`（`ts-030-system`） |
| `ts-usr-admin` | Administrator 権限を持つ管理者 IAM ユーザー（`ts-grp-admin` 所属）。**常用しない**（キーなし・コンソール専用）。`ts-030-usr-role-admin` / `ts-030-usr-build` / `ts-030-usr-operate` の作成と緊急対応のみに使います。アカウント全体の管理者のため `ts-030-` プレフィックスは付けない |
| `ts-030-usr-role-admin` | bootstrap 専用ユーザー。`ts-030-*` ロールの作成・削除（IAM 操作）権限のみを持ち、`infra/bootstrap/` を実行します。`sts:AssumeRole`・`iam:PassRole` は持たず権限昇格経路を持たない |
| `ts-usr-readonly` | 参照専用の共用 IAM ユーザー（`ts-grp-readonly` 所属）。実機確認（`info-ts-030.sh`・`tool/aws-describe-tagged-resources.sh`・describe 系）に使います。`terraform plan` は実行できません |
| `ts-030-usr-build` | infra 専用ユーザー。`sts:AssumeRole` 権限のみを持ち、`ts-030-role-build` を引き受けて `infra/`・`infra/backend/` を実行する（旧名 `ts-usr-assume-role`） |
| `ts-030-usr-operate` | データ運用専用ユーザー。`sts:AssumeRole` 権限のみを持ち、`ts-030-role-operate` を引き受けて in/out のオブジェクト操作（CLI）を行います。構築ロールは引き受けられず、インフラを破棄・再作成できません |
| `ts-030-role-operate` | データ運用ロール。`ts-030-usr-operate` のみが AssumeRole（ARN 直接信頼）。in=Put/Get/Delete/List、out=Get/Delete/List のオブジェクト操作を持つ |
| 運用ユーザー構成 | 構築・破棄・運用を管理者を常用せず回す構成（旧称「4 ユーザー運用」。現在は参照専用の `ts-usr-readonly` も使います）。bootstrap=`ts-030-usr-role-admin`、infra=`ts-030-usr-build`、データ運用=`ts-030-usr-operate`、admin は初期作成と緊急時のみ。詳細は [ユーザーとロール一覧](ユーザーとロール一覧.md) / [運用ユーザーと再作成手順](運用ユーザーと再作成手順.md) |
| IAM グループ | `ts-030-usr-*` には**未使用**（共用ユーザー `ts-usr-*` はアカウント共通のグループに所属）。用途別ユーザー＋AssumeRole で権限を分離するため、グループによる集約は行わない |
| run.conf（定義ファイル） | ジョブの内容を書く JSON。in に置くと Lambda が起動します（`.conf` がトリガー）。必須キーは `exec`（実行シェル＋入力ファイル）・`log`・`result`（out へ送るファイルのパターン）・`mail`・`sms`・`ec2_role_name`・`subnet_name`・`sg_name`・`ec2_instance_name_tag`・`output_bucket`・`ses_from_email`・`prj_prefix` の12個。任意に `instance_type`・`ebs_size`・`ebs_type`・`timeout`・`default_ami_id` など。個人情報を含むため `work/`（`.gitignore` 済み）に置く |
| user_data（`user_data_template.sh`） | EC2 の初回起動時に root で実行されるスクリプト。Lambda が run.conf の値をテンプレートに埋め込んで渡します。入力のダウンロード → `run.sh` の実行（`timeout` 付き）→ 結果のアップロード → SMS・メール通知 → `shutdown -h now`（自己 terminate） |
| CloudWatch Agent / `cloud-init-output.log` | user_data が EC2 に導入するログ転送エージェントと、user_data の出力先ファイル。`ts-030-log-ec2-010` にインスタンス ID 名のストリームで転送されます |
| Lambda 既定のロググループ | Lambda は `logging_config` を指定しないと `/aws/lambda/<関数名>`（本プロジェクトは `/aws/lambda/ts-030-lmd-010`）に自動でロググループを作ってログを出します。Terraform の管理外のため保持期間・タグが無く、destroy でも消えない（改善対象 B-6） |
| AWS CLI のロール用プロファイル | `~/.aws/config` に `role_arn` と `source_profile` を書いたプロファイル。指定すると CLI が自動で AssumeRole します。本プロジェクトの `ts-030-role-operate`（`source_profile = ts-030-usr-operate`）。tool/ の S3 操作で使う |
| `ASSUME_YES` | tool/ の upl-run.sh・del-s3.sh で、実行前の確認（y/N）を省略する環境変数（`ASSUME_YES=1`） |
| シェル雛形 skl078 | tool/ の運用スクリプトの雛形。`exec > >(tee …)` で端末とログファイルの両方に出力し、`set -e` を使わずコマンドごとの `rc` で制御します。バックグラウンド処理の標準エラーもファイルへ向けないと終了時に止まります（BUG-005） |
| EC2 の Name タグ（`ts-030-ec2-010`） | Lambda が起動する EC2 の名前（run.conf の `ec2_instance_name_tag`）。同名の EC2 が動作中なら Lambda と upl-run.sh は新しいジョブを起動しません。pop-s3.sh・del-s3.sh はこの EC2 が動作中なら中止します |
