## BUG-001：構築ロールの ENI 権限不足で subnet を destroy できない

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-06-22 |
| 対象 | `infra/bootstrap/iam_build_role.tf`（構築ロール `ts-030-role-build`） |
| 工程 | `infra` の `terraform destroy`（プロファイル `ts-030-usr-build` → AssumeRole） |
| 修正コミット | `98d683d` |

### 事象

`terraform destroy` が **subnet 削除の段階で失敗**しました。IGW・ルートテーブル・関連付けの削除までは成功し、subnet で停止しました（VPC は未削除のまま残存）。

```
Error: deleting ENIs for EC2 Subnet (subnet-...):
listing EC2 Network Interfaces: ... StatusCode: 403 ...
api error UnauthorizedOperation: User: arn:aws:sts::***:assumed-role/ts-030-role-build/...
is not authorized to perform: ec2:DescribeNetworkInterfaces
because no identity-based policy allows the ec2:DescribeNetworkInterfaces action
```

### 原因

構築ロール `ts-030-role-build` のポリシーに **`ec2:DescribeNetworkInterfaces`（ENI の一覧取得）権限が欠落**していました。

subnet は内部に ENI が残っていると削除できない（`DependencyViolation`）ため、AWS provider は subnet 削除前に必ず次の順で動きます。

```
① ec2:DescribeNetworkInterfaces  … 残 ENI の有無を確認   ← ここで 403
② （残あれば）DetachNetworkInterface / DeleteNetworkInterface で掃除
③ ec2:DeleteSubnet               … subnet 本体を削除
```

①の**確認**権限が無く、ENI が実際には無い（EC2 未起動）にもかかわらず「確認自体ができず」エラーになりました。

### 真因（なぜ作り込まれたか）

- 構築ロールの権限を、作成に必要な API だけから洗い出していたため、**この権限が最初から入っていませんでした**。
- CLI で `aws ec2 delete-subnet` を直接実行する場合は provider のような事前 ENI 確認を行わないため、CLI での動作確認では**顕在化しませんでした**。
- Terraform で破棄まで実行したことで初めて表面化しました。

### 修正

`EC2VPCManagement` ステートメントに ENI 関連3アクションを追加しました。

```hcl
"ec2:DescribeNetworkInterfaces", "ec2:DetachNetworkInterface", "ec2:DeleteNetworkInterface",
```

| アクション | 役割 |
|------------|------|
| `DescribeNetworkInterfaces` | 今回直接効いた**確認**権限 |
| `DetachNetworkInterface` / `DeleteNetworkInterface` | 将来 EC2 起動後の破棄で残 ENI を掃除するための備え |

### 対応手順

1. `infra/bootstrap/iam_build_role.tf` を修正
2. `infra/bootstrap` で `terraform apply`（`ts-030-usr-role-admin`）→ ロールのポリシー更新
3. `infra` で `terraform destroy` 再実行 → subnet・VPC 削除完了

その後、2ユーザー運用で destroy → recreate の全サイクル（infra destroy → bootstrap destroy → bootstrap apply → infra apply）を実行し、正常動作を確認済みです。

### 再発防止・教訓

- IAM ロールの権限は「作成系」だけでなく**「削除系が呼ぶ付随 API（Describe 等）」も含めて**洗い出します。
- 権限を CLI の操作から洗い出す場合は、**CLI では呼ばれない provider 固有の確認ステップ**に注意します。
- 後続リソース（Lambda・EC2 等）の構築でも、destroy まで通して検証します。

## BUG-002：構築ロールの read-after-write / refresh 権限不足で apply/plan が 403

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-07-07 |
| 対象 | `infra/bootstrap/iam_build_role.tf`（構築ロール `ts-030-role-build`） |
| 工程 | `infra` の `terraform plan` / `apply`（WBS 2.3 = S3 + 依存の IAM/Lambda） |
| 修正コミット | `dc9f463` |

### 事象

WBS 2.3 の plan / apply が、リソース作成後の**読み取り（refresh / read-after-write）段階で 403** となり、3 回に分けて権限不足が連続的に表面化しました。

```
① plan 時: Error: reading VPC Security Group Rule (sgr-...): ...
   UnauthorizedOperation ... not authorized to perform: ec2:DescribeSecurityGroupRules
② apply 時: Error: reading Lambda Function (ts-030-lmd-010) latest version: ...
   AccessDeniedException ... not authorized to perform: lambda:ListVersionsByFunction
③ （事前に判明）aws_iam_role_policy の refresh に iam:GetRolePolicy が必要
```

### 原因

構築ロール `ts-030-role-build` に、**Terraform が「作成した直後に必ず読み戻す」際に呼ぶ Describe/Get 系権限が欠落**していました。作成（Create/Put）系は揃っていましたが、read 系が不足していました。

| 欠落していた権限 | どこで呼ばれるか |
|------------------|------------------|
| `iam:GetRolePolicy` | `aws_iam_role_policy` の refresh |
| `ec2:DescribeSecurityGroupRules` | 既存 SG ルール（2.2 作成）の refresh |
| `lambda:ListVersionsByFunction` / `GetFunctionCodeSigningConfig` / `GetRuntimeManagementConfig` | `aws_lambda_function` の read |
| `s3:GetBucketAcl` / `GetBucketCORS` / `GetBucketWebsite` / `GetAccelerateConfiguration` / `GetBucketRequestPayment` / `GetBucketLogging` / `GetReplicationConfiguration` / `GetBucketObjectLockConfiguration` | `aws_s3_bucket` 作成後の read-after-write |

### 真因（なぜ作り込まれたか）

- BUG-001 と**同じ構造**です。構築ロールの権限を作成系の API 中心に洗い出していたため、read 系権限が薄くなっていました。
- CLI の `aws s3api create-bucket` 等は作成するだけで、**Terraform のように作成直後に十数個の GetBucket\* を読み戻す挙動が無い**ため、CLI での確認では顕在化しませんでした。
- 特に SG ルール（2.2）は apply 時は create 応答で state を書けたため成功したが、**2.3 の refresh で初めて `DescribeSecurityGroupRules` 不足が表面化**しました（潜在不具合）。

### 修正

`iam_build_role.tf` の各ステートメントに read 系権限を追加しました（いずれも読み取り専用）。

- `IAMManagement` ← `iam:GetRolePolicy`
- `EC2VPCManagement` ← `ec2:DescribeSecurityGroupRules`
- `LambdaManagement` ← `lambda:GetFunctionCodeSigningConfig` / `ListVersionsByFunction` / `GetRuntimeManagementConfig`
- `S3Management` ← 上表の GetBucket\* 系 8 アクション

### 対応手順

1. `infra/bootstrap/iam_build_role.tf` に不足権限を追加
2. `infra/bootstrap` で `terraform apply`（`ts-030-usr-role-admin`）→ ロール更新（本件は計3回に分けて実施）
3. `infra` で `plan` → `apply` → 再 `plan` で `No changes`（冪等）を確認

### 再発防止・教訓

- **Terraform の read（refresh / read-after-write）は CLI 版より広い Describe/Get 権限を要します**。新サービスを Terraform で構築する際は、Create/Put だけでなく対応する Get/List/Describe をセットで付与します。
- 特に `aws_s3_bucket` は作成後に多数の `GetBucket*` を読み戻すため、read 系を厚めに用意します。
- create が通っても**次回 plan の refresh で潜在不足が出る**ことがあります。作成後に必ず再 `plan` を実行し `No changes` まで確認します。

## BUG-003：端末のディスク故障で tfstate を消失

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み（`infra/`・`infra/bootstrap/` とも import で復旧後、全削除→再構築を実施。再発防止として `infra/` の state を S3（`ts-030-bkt-tfstate`）へ移行済み（B-5）） |
| 検出日 | 2026-09-21 |
| 対象 | `infra/terraform.tfstate`・`infra/bootstrap/terraform.tfstate`（現在 `infra/` の state は S3 の `infra/terraform.tfstate`。移行前のローカル state は `infra/terraform.tfstate.pre-s3` に退避） |
| 工程 | 新端末 pc01（Debian 13）への移行時 |
| 記録 | `run-terraform.log`（端末の実行ログ。公開版には含めていません） |

### 事象

旧端末のディスクが故障し、Git 管理外の tfstate が2つとも失われました。AWS 上のリソースは残っていました。

### 原因

state をローカルファイルのみで保持しており、バックアップも remote backend もありませんでした（`.gitignore` で除外しているため Git にもありません）。

### 影響

state 無しで `apply` すると、名前の一意制約が無い VPC/Subnet/SG 等は**二重作成**され、S3/IAM 等は AlreadyExists で失敗します。

### 対応手順（infra/）

1. `aws-describe-tagged-resources.sh` の出力と describe 系 CLI で既存リソースの ID を収集
2. 一時ファイル `infra/imports.tf` に `import` ブロック35個（for_each 展開で44リソース）を記述
3. `terraform plan -out=tfplan` → `44 to import, 0 to add, 1 to change, 0 to destroy`（change は意図した lmd-010 のコード更新のみ）を確認
4. `terraform apply tfplan` → `imports.tf` を削除 → 再 `plan` で `No changes`

### 対応手順（infra/bootstrap/、2026-09-22）

1. `terraform import aws_iam_role.build ts-030-role-build`
2. `terraform import aws_iam_role_policy.build ts-030-role-build:ts-030-role-build-policy`
3. その後、`infra` → `bootstrap` の順で全削除し、`bootstrap` → `infra` の順で再構築（途中で BUG-004 が発生）

### 再発防止・教訓

- ローカル state は端末故障で失われます。→ 2026-09-22 に `infra/` の state を S3 バックエンドへ移行済み（[改善対象.md の B-5](改善対象.md#バックアップ災害復旧)）。
- `import` ブロック（Terraform 1.5+）なら ID を宣言的に書け、`plan` で取り込み結果と差分を事前確認できます。

## BUG-004：構築ロールの削除系権限不足で infra の destroy が途中停止

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-09-22 |
| 対象 | `infra/bootstrap/iam_build_role.tf`（構築ロール `ts-030-role-build`） |
| 工程 | `infra` の `terraform destroy`（全削除→再構築の削除側） |
| 修正コミット | `ed287e5`（IAM）／`8368bc4`（S3） |
| 記録 | `run-terraform.log`（端末の実行ログ。公開版には含めていません） |

### 事象

`terraform destroy` で 44 リソース中 40 が削除され、IAM ロール3本と CloudTrail ログ用バケットが残りました。

```
# CloudTrail イベント履歴（1回目の destroy）
AccessDenied ... ts-030-role-build ... is not authorized to perform: iam:ListInstanceProfilesForRole
DeleteBucket ts-030-bkt-cloudtrail-logs  BucketNotEmpty

# 2回目の destroy（IAM 修正後）
Error: emptying S3 Bucket (ts-030-bkt-cloudtrail-logs): ... version (null): AccessDenied:
... is not authorized to perform: s3:DeleteObject on resource: "arn:aws:s3:::ts-030-bkt-cloudtrail-logs/AWSLogs/..."
```

### 原因

1. Terraform の `aws_iam_role` 削除は、事前に `iam:ListInstanceProfilesForRole` で紐づく Instance Profile を確認しますが、この権限が構築ロールにありませんでした。
2. `force_destroy = true` のバケットを空にする際、**バージョニング無効バケットのオブジェクト（version=null）の削除は `s3:DeleteObject` で評価されます**。構築ロールには `s3:DeleteObjectVersion` しかありませんでした。

### 真因（なぜ作り込まれたか）

これまでの destroy は、中身の無いバケットと Instance Profile 付け替え前の状態でしか検証しておらず、削除系の権限を網羅的に試していませんでした（BUG-001/002 は作成・読取系）。

### 修正

- IAM 権限に `iam:ListInstanceProfilesForRole` を追加しました。
- 別 Statement `S3EmptyProjectBuckets` で `s3:DeleteObject` を追加しました。データ削除権限のため Resource を `arn:aws:s3:::ts-030-*/*` に限定しています。
- CloudTrail ログ用バケットに `force_destroy = true` を設定しました（`ad700af`）。証跡が常時ログを書くため、無いと BucketNotEmpty で必ず失敗します。

### 対応手順

1. bootstrap を import（BUG-003）→ 権限追加 → `bootstrap` apply（2回）
2. `infra` の `terraform destroy` を再実行 → 残り4リソース削除（バケットは約41,000オブジェクトを1分5秒で削除）
3. `bootstrap` destroy → apply、`infra` apply（44 added）→ 再 plan `No changes`

### 再発防止・教訓

- 構築ロールの権限は作成・読取だけでなく**削除系も destroy の実行で検証します**。特に中身のある S3 バケットは空バケットと別経路（オブジェクト削除）を通ります。
- バージョニング無効バケットのオブジェクト削除は `s3:DeleteObject`、有効バケットのバージョン削除は `s3:DeleteObjectVersion`。`force_destroy` を使うなら両方必要です。
- `destroy.sh` を使わずに実行するとログが残らず、原因特定が遅れます。削除は必ずログを残します。

## BUG-005：tool/run.sh がエラーで終わると tee の終了待ちで止まり、EC2 が終了しない

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-09-22（docs・コード整合確認） |
| 対象 | `tool/run.sh`（EC2 上で user_data が ec2-user で実行） |
| 修正コミット | `42a1ffd` |

### 事象・原因

- アクティビティ取得を `bash /tmp/simple-act > simple-act.log &` で起動していました。標準出力だけをファイルへ向け、**標準エラーは雛形の `exec > >(tee …) 2>&1` のパイプを引き継いでいました**。
- エラーで main から return すると、アクティビティ取得を止めないまま後処理の `exec 1>&- 2>&-; wait "${TEE_PID}"` に進みます。バックグラウンドがパイプの書き込み側を握り続けるため tee に EOF が届かず、**wait が永久に返りません**（EXIT の trap にも到達しません）。
- user_data の `su -` が戻らず `shutdown -h now` に進まないため、**EC2（既定 c6i.4xlarge）が動き続けて課金が続きます**。

### 再現（2026-09-22）

| 環境 | 修正前 | 修正後 |
|---|---|---|
| 手元 bash 5.2（最小再現スクリプト） | 10 秒で打ち切り（止まった） | 即終了 |
| Amazon Linux 2023 コンテナ（bash 5.2、実物の run.sh） | 30 秒で打ち切り（止まった） | 即終了 |
| Amazon Linux 2 コンテナ（bash 4.2、実物の run.sh） | 即終了 | 即終了 |

Amazon Linux 2（現在の既定 AMI）は bash 4.2 のため、プロセス置換を `wait` できず（終了コード 127）すぐ戻り、止まりません。AL2023 への移行（改善対象 B-7）で顕在化する不具合でした。

### 修正

- バックグラウンドの標準エラーもファイルへ向けます（`> simple-act.log 2>&1 &`）。
- main の直後で必ずアクティビティ取得を止めます（trap に頼りません）。
- 保険として run.conf の `timeout` で run.sh を打ち切るようにしました（user_data、未指定時 21600 秒）。

### 再発防止・教訓

- `exec > >(tee …)` を使うシェルでバックグラウンド処理を起動するときは、その標準出力・標準エラーの両方をパイプから外します（CLAUDE.md に記載）。
- EC2 上で止まると課金が続くため、実行時間の上限（timeout）を必ず設けます。

## BUG-006：Lambda の「起動しかけの EC2 を削除」経路に権限が無い

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-09-22（docs・コード整合確認） |
| 対象 | `infra/iam.tf`（`ts-030-role-lambda-010`）・`infra/lambda/lambda_function.py` |
| 修正コミット | `42a1ffd` |

### 事象・原因

`lambda_function.py` は、EC2 が時間内に running にならないとき `terminate_instances` で起動しかけのインスタンスを削除します。しかし WBS 2.4e の最小権限見直しで Lambda ロールから `ec2:TerminateInstances` を削除しており（終了処理の簡素化で不要になったと判断）、この経路は AccessDenied になって EC2 が残る状態でした（実際には発生していません）。

### 修正

`ec2:TerminateInstances` を、Lambda が起動時に付けるタグ `autogen-by = <prj_prefix>-system` を持つインスタンスに限定して追加（Condition `ec2:ResourceTag/autogen-by`）。IAM ポリシーシミュレーターで、タグ一致は allowed、不一致は implicitDeny を確認しました。

### 再発防止・教訓

権限を削るときは、その権限を使うコード経路（例外処理の中を含む）を検索してから削ります。

## BUG-007：exec が1語だと実行シェル名が入力ファイル扱いになる

| 項目 | 内容 |
|------|------|
| 状態 | ✅ 修正済み |
| 検出日 | 2026-09-22（docs・コード整合確認） |
| 対象 | `infra/lambda/user_data_template.sh` |
| 修正コミット | `42a1ffd` |

### 事象・原因

`INPUT_FILES=$(echo $EXEC_COMMAND | cut -d' ' -f2-)` は、区切り文字を含まない行をそのまま返す `cut` の仕様により、exec が `"run.sh"` の1語だと `run.sh` を返します。その結果 `./run.sh run.sh` が実行される（現在の run.conf は入力ファイルを指定しているため未発生）。

### 修正

`read -r EXEC_SCRIPT INPUT_FILES <<< "$EXEC_COMMAND"` に変更しました（1語なら INPUT_FILES は空）。1語・複数語・パターンを含む場合を手元で確認しました。
